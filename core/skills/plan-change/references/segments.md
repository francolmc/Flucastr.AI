# Stories and segments

11. **Stories and segments.** A feature uses one branch and one `plan.md`. Each self-contained story may use one segment or group several consecutive small segments under the same user outcome. Each segment has a scope of up to three product files, its own A# criteria, atomic TODOs naming files and checks, verification, and evidence; the story includes the user and value, dependencies, WHEN/THEN, and handoff. Each story must be buildable and verifiable on its own against the base; if it depends on another, explain which result it needs and why, and order it afterward. Keep stories small, preferably bounded by file, without splitting a flow into isolated functions that are not useful outcomes. If the environment has not been verified, the first segment covers only the environment (install, start, reproduce), with no code changes. Without `continuity: continuous`, the planner launches one segment at a time; with it, the builder continues through approved segments of the same story in order, subject to `## Stop conditions`. A plan with two or more segments of the same story should declare `continuity: continuous` by default; `review-plan` warns when two or more segments lack it. Each segment's completion criterion is measurable: its `Segment verification:` names a command and its expected result (exit code or output), not a general description. Adjust later segments after seeing the previous segment's actual state. Older plans with traditional steps or segments remain executable. To limit builder context when needed, put some stories in `tramo-N.md` files linked from `plan.md`, each with its story, steps, `Segment verification:`, and evidence; the index retains frontmatter, objective, exploration if applicable, assumptions, decisions, validation, scope, verification, and the ordered story list with status. Neither size nor story count alone requires externalizing stories. The builder reads `plan.md` and only the active `tramo-<n>.md`, not other segment documents. At the end of each story, use `/compact` or a new session so the planner reviews in a fresh context. A plan may require review per segment, including for high-risk work; if declared, it blocks progress until the verdict. A final review preserves continuity but may find accumulated defects; reviewing each segment finds them sooner, with more pauses and reviews. In either case, each segment checkpoint records files, a diff summary, and verification, and suggests a story commit for the user to make, without committing. Record a minor decision resolved during the change as a new row in `decisions.md`; in a plan without that file, as `Resuelto: <date> <decision>` under `## Decisions already taken`. Each `Segment verification:` declares its level (rule 13); Level 3 is only for the final acceptance run in the last story.

15. **Verifiable segments.** Each segment is judged by a machine when it ends. It declares (a) the A# it covers (`covers A1`; every A# of the segment is covered); (b) `Segment verification:` = one Level 1 quick check (host, no services, seconds; a targeted test counts) with exact command, `level 1` and expected exit; (c) a `Handoff:` with a concrete example (optional with `format: 2`). One functional unit per segment: two A# touching disjoint files are two segments. Level 2 only in the last segment of a story; Level 3 only in the plan's last segment. Split further only if it adds an independently checkable A#; else merge. Explain residual warnings in one line.

## Continuity and sensitivity

To enable continuity, set `continuity: continuous` in the frontmatter; if omitted, the plan keeps one segment active at a time. In continuous mode, a story may have several small, ordered tramos, each with its own scope, criteria, steps, and verification; the builder runs them in sequence until the story ends or a stop condition applies. Group them under the same user outcome and declare no more than three product files per tramo. Also declare `Revisión: fin de historia` or `Revisión: por tramo`; the second is optional even for high risk, but once declared it blocks progress until the review. Record a baseline measurement of each check command: exact command, observed duration, and environment. Each tramo leaves a checkpoint with files changed, a diff summary, and the check result; at the end of the story, suggest a commit for the user to make, without creating it.

For new tests, add a sensitivity check (an invalid input or an isolated mutation that fails for the expected reason) only for high-risk A#, that is, those touching the list in condition 4 of `planner.md`. If an empty list could accept everything, require non-empty inputs or discovered cases. No mutation is needed for every phrase or administrative step.
